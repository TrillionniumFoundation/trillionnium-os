# Acceptance r5: exact combination binding

This host-only package fixes an accounting issue: the frozen provider-r5/qa protocol is the unchanged r4 protocol and still names source seal700e5… . Feeding r5 samples into the old aggregator directly would exclude them as historical. The original protocol, old aggregator, old materializer and all historical results remain unchanged.

## What is bound

The new protocol names provider-r5 source seal `f3685aadb004882a3f087e42d43d374bd24564ad56eb472cb638b2f88e96935f`, service-inputs-r3 `ccb7cacf0dd9e4e12daba09515a56633363dd9f04607b44546df1e493d15bfd2`, and production config `0eb740aea8591a0377bc9ceecafb4b848a9dcdd7dc2cb75ffc3f0892abe5c755`.

The original19 case objects, order, all pass conditions, limits and geometry are compared for exact decoded equality before every aggregation or materialization. The new file changes only the release/source metadata, pending prerequisite wording, and an explicit r5 binding record. The references directory contains byte-identical original protocol and helper sources; their exact hashes are checked before use.

The original limits remain7 tools,8 model rounds and300 seconds per turn. Display0/1224×2992/rotation0 remains the declared baseline. Preserving these values does not establish physical qualification on the new executor/policy.

Source seal alone is insufficient. The selected combination also requires these real artifact hashes:

- Final production module manifest.
- The exact policy-rules input manifest, including the selected IPC revision and business delta.
- Actual live policy snapshot and its corresponding semantic audit.
- The native runtime and installed App input manifest.

The already fixed service manifest covers model weights/projector/CPU runtime, executor/worker/client, helper JAR bytes, model parameters and device firmware fingerprint. No API key contents or private user text belong in a combination manifest.

COMBINATION-PENDING.json deliberately uses null for the five remaining inputs. It is not installable or qualified metadata. Only a new Root-reviewed immutable file with all actual pins and state=frozen can admit executed samples or generate a fresh request. The wrapper does not itself establish that an artifact is installed merely from a hash-shaped string; Root's referenced deployment and qualification evidence is required.

## Grouping and zero-sample result

`aggregate_protocol_r5.py` hashes the complete normalized combination and retains the selected manifest's original byte hash. Every current attempt must match both that complete identity and the selected source. Different module or policy pins produce different combination IDs even when source remains identical.

A foreign r5 combination is only described as verified when its separate original manifest is supplied and hash-checked. A current-source executed row with missing/unverified combination provenance is retained outside the current denominator and also prevents the19-case gate from closing. Old-source records remain explicitly excluded history; they are never rewritten.

The actual input files EMPTY-ACTUAL-ATTEMPTS.json and EMPTY-AUXILIARY-EVIDENCE.json are empty arrays. A real host run produced validation/EMPTY-CURRENT-REPORT.json with19 BLOCKED cases, model business N=0, success fraction=null, no latency or usage samples, full combination pending, and daily-use qualification=false. Eighteen targeted host checks verified these results and the metadata/grouping boundaries. Constructed nonempty rows in those checks are explicitly synthetic and never enter an actual quality report.

The wrapper performs no phone, model, service, socket, native task, policy or ledger operation. Its own actual_phone_actions=0 describes the report operation, not the number of effects that may appear in future input evidence.

## Commands and required records

The already executed zero report used:

```sh
python3 -B aggregate_protocol_r5.py --combination COMBINATION-PENDING.json --combination-sha256 f5f778e908e46f2c291da06a08dc9546ac803350e6ec9989582564d1ca3de086 --attempts EMPTY-ACTUAL-ATTEMPTS.json --auxiliary EMPTY-AUXILIARY-EVIDENCE.json --out validation/EMPTY-CURRENT-REPORT.json
```

Output creation is exclusive: do not rerun this command against the same output path. A new review uses a new output filename and the exact read-back hash of the selected combination.

A current attempt uses the existing frozen aggregator fields plus `combination_sha256` and `combination_manifest_sha256`. It preserves an immutable attempt ID, case ID, layer, task outcome, protocol result, fresh nonce where required, exact original evidence hashes, and an independent collector report for model E2E. The combination values are recorded in material.json and the selected zero/baseline report; they are never guessed.

A verified foreign r5 attempt additionally supplies `combination_manifest: {path, sha256}` for its own separate original combination manifest. Do not relabel it to the current combination.

Health, the one-shot r6 native printf probe, recovery dispositions, and host validations go only in a separate auxiliary array. Each item has exactly `kind`, `path`, `sha256`, `observed_status`; kind is health/native_component/recovery_event/host_validation. Original evidence bytes are verified, but the status is identified as the operator's classification rather than an automatically established PASS. These records never close a fixed19 case or increase the model business denominator.

COMP-01 in the actual protocol is the explicit HEPTA return component. It is not the new r6 printf probe. A probe record supplied as a new fixed19 case ID is rejected.

## Fresh materialization after the full combination is frozen

`materialize_case_r5.py` supports health, visual and Unicode. It loads the byte-pinned original materializer and rebinds only its source metadata to r5. Request wording, postconditions, fresh entropy and exact Unicode handling are unchanged. It additionally records the full combination identity and copies the original combination bytes into the new private material directory.

The CLI requires `--combination`, its actual `--combination-sha256`, and a new `--out` directory. Pending/null combinations are rejected before nonce generation or output creation. Materialization never registers, sends, retries or restores a task. E2E-03/04 still require fresh public-view qualification and separately prepared exact conditions; this helper does not fabricate those fields.

New genuine local model health must first produce its real terminal under the final production combination. The native component probe, host metadata checks and previous r4 health are not a substitute. Source/request material generation is not evidence that the task passed.

## Report interpretation

Protocol PASS/FAIL/BLOCKED is separate from actual task outcome complete_success/partial/failed/cancelled/unconfirmed. A negative case can pass its expected rejection or cancellation while its task does not become a business success. Recovery is a separate event on the original task; a resolved original failure remains failed.

The five lifecycle cases NEG-04/05/07/08/09 require both isolated and physical-native evidence. Old r5 sidecar fixtures and the new r6 IPC probe do not automatically close them. NEG-08's old candidate r1 has known review gaps and is not a ready r6/nonempty-draft harness. Missing layers stay BLOCKED.

Money and hardware energy remain null unless measured from real evidence. CPU-model HTTP usage, end-to-end observed latency, polling interval, actual resource measurements and recovery results must retain their sample counts and scope. A process VmHWM reading is a process-lifetime high-water mark, not a per-task peak. Even a single full19 suite does not establish broad daily-use reliability.
