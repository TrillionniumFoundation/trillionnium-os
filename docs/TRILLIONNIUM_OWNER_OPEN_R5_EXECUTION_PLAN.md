## 0. Authority, scope and truth rules

R3 remains normative for product semantics. Codex is the only semantic principal:
it chooses intent, context, target, tool, exact command/argv, retry,
compensation and interpretation. Broker, transport, core, runtime, stores and
supervisors own only mechanism: framing, identity, resource bounds, process
lifecycle, transport, persistence, inspection, recovery and evidence.

R5 is the active implementation and qualification sequence. This r6 revision
supersedes the previous R5 plan text where it described repository closure more
strongly than the current source supports.

The following rules are non-negotiable:

1. A checked-in plan or status file is not exact-head execution evidence.
2. Exact-head evidence is generated by CI from `GITHUB_SHA`, Git tree, lockfile,
   workflow/run/job identities and artifact hashes.
3. A historical green commit does not validate a later commit.
4. A source fixture cannot promote installed Codex, Root Linux placement,
   Android image, physical ADB, destructive fault or public-release claims.
5. An accepted but uncertain effect is never automatically redispatched.
6. A capacity rejection may claim `not_started` only when it occurs before any
   spawn/effect attempt.
7. Storage failure is not proof that an effect did not start.
8. Client EOF, delivery backpressure or broker disconnect is not cancellation.
9. Public release remains false until a separately authorized L6 profile closes.
10. Every claimed guarantee must appear identically in code, protocol,
    machine status, workflow and evidence.

## 2. Intended product topology

```text
AiShell / owner clients / local Codex MCP
  -> one owner-open product entrypoint
  -> optional same-trust-domain connection broker
  -> bounded transport carrier
  -> job-aware execution core
  -> one provider/Codex semantic turn
  -> direct shell, ordinary adb, or durable shell.job process
  -> raw observation returned to the same turn
  -> provider continues
  -> exactly one turn terminal
```

The process topology may contain several operating-system processes while still
having one semantic principal. The authority boundary is:

| Component | May interpret intent | May rewrite command/argv | May select target/provider | May retry uncertain effect | May apply mechanical bounds | May persist observations |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Codex/provider | yes | authors request | yes | only after inspecting truth | yes for its own protocol | optional |
| Broker | no | envelope correlation only | no | no | yes | yes |
| Transport | no | sequence/delivery metadata only | no | no | yes | yes |
| Core | no | canonical framing only | no | no | yes | yes |
| Runtime/job manager | no | no | no | no | yes | yes |
| Android/init/Root Linux supervisor | no | launch configuration only | no semantic fallback | no | yes | lifecycle evidence |

Any source path that introduces plan reconstruction, risk classification,
semantic approval, target substitution, serial/host/port injection, provider
fallback or effect retry into a non-provider component is outside R5.

## 3. Global effect state machine

Every effectful turn, call, job start or job control is described by these
mechanical stages:

```text
received
  -> validated
  -> capacity_reserved
  -> accepted_durable
  -> spawn_or_forward_attempted
  -> started_or_forwarded_durable
  -> zero or more observation_durable / delivery_attempted
  -> terminal_durable
  -> terminal_delivery_attempted
```

Permitted conservative terminal states include:

```text
rejected_before_acceptance
spawn_failed
completed_durable
completed_observed_undurable
cancelled_observed
timed_out_observed
unknown_after_disconnect
unknown_after_timeout
unknown_after_journal_failure
unknown_after_cleanup_failure
reconciliation_required
```

### Crash interpretation

| Crash cut | Minimum truthful result | Automatic redispatch |
| --- | --- | ---: |
| before durable acceptance | rejected/not accepted when no effect attempt is proven | caller may submit a new request |
| after acceptance, before effect attempt, but no no-spawn proof | uncertain | no |
| after spawn/write/remote attempt, before durable started/forwarded | effect may have started | no |
| after started/forwarded, before terminal | unknown/reconciliation required | no |
| after terminal durable, before delivery | replay exact terminal | no |
| after terminal delivery | exact duplicate replay is permitted | no |

Detailed field and transition requirements are normative in
`protocols/owner-open-effect-state-machine-v1.md`.

## 4. Evidence levels and promotion

| Level | Meaning | What does not count |
| --- | --- | --- |
| L0 | parsed contract, graph and source-shape checks | authored tests |
| L1 | exact-checkout unit/property/process tests | installed-target claims |
| L2 | installed target Root Linux Host/broker/provider/Codex integration | local host fixtures |
| L3 | clean Android image, Soong/init/SELinux and target-files evidence | overlay source alone |
| L4 | authorized physical same-turn shell/job/ordinary-ADB effects | fake adb |
| L5 | provider/Host/broker/client crash, USB loss, reboot, ENOSPC and power-loss qualification | ordinary success path |
| L6 | signed release, AVB/rollback/OTA, key custody, multi-user and human authorization | CI success alone |

A gap closes only when its required source and exit-level evidence are both
bound. `SOURCE_CLOSED_PENDING_EVIDENCE` is a valid state; it is not zero-gap.

## 11. Zero-gap and release rule

`zero_gap=true` is legal only when every entry in
`status/owner-open-r5-gap-closure.json` is `CLOSED` with evidence at or above its
declared exit level.

Repository source and documentation can close repository blockers. They cannot
synthesize target Root Linux, Android image, physical device, destructive fault
or release evidence. Those remain `EXTERNAL_HOLD` until the actual environments
produce the required records.

`public_release` remains false until `R5-GAP-RELEASE-001` is closed by a
separate signed profile and explicit human authorization.

## Permanent external-evidence program

The only supported L1-governance and L2–L6 promotion path is defined by
`operations/owner-open-r5-external-evidence-capture-and-promotion.md`. Target
workflows emit capture-only bundles; a distinct human review attestation makes
a byte-identical capture promotable. The canonical gap verifier recursively
rehashes every checked-in bundle artifact and rejects secret-shaped content,
undeclared files, stale source identity, synthetic evidence and self-review.

Temporary self-modifying gap-promotion workflows are retired.
